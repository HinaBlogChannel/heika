# 秘密の扱い

秘密鍵、ニーモニック、シード、拡張鍵のチェーンコード、鍵の共有で導出した値を秘密として扱う。この文書は、コードからは読み取りにくい方針とその理由をまとめる。

## 入力

- 秘密は標準入力からのみ読む。引数で受け取ると、シェルの履歴や `/proc/<pid>/cmdline` に残るためである。ファイルはリダイレクトで渡す。
- 標準入力が端末のときは、Unix では termios の ECHO を切って、Windows ではコンソールのモードの ENABLE_ECHO_INPUT を切って、打った文字を画面に出さずに読む。読み終えたら元に戻す。
  - ISIG（Windows では ENABLE_PROCESSED_INPUT）も切るので、読んでいるあいだは Ctrl-C で落ちない。落ちると、文字を出さないままの端末が残るためである。Ctrl-C は文字として入り、読めない入力として弾かれる。やめるときは、何も入れずに Ctrl-D（Windows では Ctrl-Z と Enter）を押す。
  - Unix と Windows のほかでは文字を出さずに読む方法を用意していないので、端末のときは読まずにエラーにする。
- Unix では標準入力のファイル記述子を、Windows ではハンドルを複製し、バッファなしの `File` として読む。std の `Stdin` はプロセス全体で共有するバッファを持ち、その中身を消せないためである。Windows のコンソールからはコンソールのコードページのバイトで読むが、秘密鍵の16進とニーモニックは ASCII なので変わらない。
- 入力は 1024 バイトの固定長バッファに読み、それを超えたらエラーにする。

## 出力

- 秘密はファイルにのみ書き、標準出力には出さない。公開鍵やアドレスは標準出力に出す。
- `heika harvesting --delegate` が作るリモートアカウントと VRF の秘密鍵は、委任先のノードの公開鍵あてに暗号化して委任の要求に入れるだけで、ファイルにも書かない。ユーザーが持っておく必要がなく、次に委任先を変えるときはまた作り直すためである。
- 投票鍵のファイルは、エポックごとの子の秘密鍵が入るので、秘密鍵と同じく 0600 で書く。ノードが読むファイルの形そのものなので、子の鍵は暗号化しない。根の秘密鍵はどこにも書かない。根の鍵が残ると過去のエポックの投票を作り直せるので、catapult の votingkey と同じく、子の鍵に署名したら捨てる。
- ファイルは `create_new` で作り、既存のファイルを上書きしない。Unix では権限を 0600 にする。
- 改行は秘密とは別に書く。秘密の `String` に改行を足すと、領域が取り直されて古い領域が残るおそれがあるためである。

## メモリ

- 秘密は `Zeroizing` に入れ、drop 時に 0 で上書きする。途中の値（エントロピー、単語の番号、HMAC の出力など）も同じにする。
- 秘密の `String` を伸ばさない。長さが決まっている固定長のバッファで組み立ててから `String` にする。
- 秘密を持つ型は `Display` を持たず、`Debug` は `PrivateKey(..)` のように中身を出さない。
- 標準出力が閉じられたときも `process::exit` せずに `main` まで戻る。途中の値を drop させるためである。
- PBKDF2 の最後のブロックの中間値は、依存ライブラリの中でスタックに残る。シードはすべてのブロックの XOR なので、1 つだけでは復元できないとして許容している。
- 公開鍵の導出と署名では、curve25519-dalek がスカラー倍算の途中でスカラーを桁ごとに分けた配列を作り、それを 0 で上書きしない。秘密鍵のスカラーと nonce がこの形でスタックに残る。nonce と署名がそろうと秘密鍵のスカラーが求まるので重い残留物だが、消すにはスカラー倍算を自分で書くしかないので許容している。
- 鍵の共有でも、curve25519-dalek のスカラー倍算に同じ残留物がある。秘密鍵（委任ハーベストの要求では使い捨ての鍵）のスカラーがスタックに残る。
- 鍵の共有の HKDF は、HMAC を2回呼ぶ形で自分で書いている。hkdf crate は途中の鍵を 0 で上書きしないためである。共有した点、途中の鍵、共有鍵は `Zeroizing` に入れる。AES-GCM の鍵の展開は、aes-gcm の `zeroize` フィーチャーで消す。
- TLS で名乗るときは、秘密鍵を PKCS#8 の DER にして rustls に渡す。rustls と ring は秘密鍵を自分で持ち、0 で上書きしない。TLS を使う以上は避けられないので許容している。

## 時間

- 秘密鍵と 16 進の変換には `base16ct` を使い、文字によって処理時間が変わらないようにする。公開データ用の 16 進の変換は別にある。
- 秘密鍵の PEM の Base64 との変換には、定数時間の `base64ct` を使う。PEM の枠は自分で外し、本体をまとめて変換する。PEM 用の crate のデコーダーは、途中の数バイトを内部のバッファに残すためである。
- BIP 39 の単語の照合では、2048 語すべてを走査し、比較と選択に `subtle` を使う。

## エラー

- エラーには、秘密のどの位置の何が悪かったかを含めない。打ち間違いを伝えるつもりで秘密の一部を漏らさないためである。

## 乱数

- 鍵やニーモニックの生成は、暗号用の乱数を引数で受け取る `generate_with_rng` が基本である。OS の乱数を使う `generate` は `getrandom` フィーチャーで外せる。

## パスフレーズ

- `heika key derive` は BIP 39 のパスフレーズを空にする。公式のデスクトップウォレットと同じである。
- ライブラリでは、パスフレーズは ASCII のみ、256 バイトまで受け付ける。

## キーストア

`heika wallet` のキーストアは、ここまでの「秘密は標準入力からだけ読む」「秘密はファイルに1つずつ書く」の例外になる。ファイルの形式は [keystore.md](keystore.md) にまとめてある。

- パスフレーズは、標準入力ではなく、端末（Unix では `/dev/tty`、Windows では `CONIN$`）を開いて聞く。標準入力は、取り込む秘密を渡すのに使うためである。打った文字は出さず、Enter で終え、Ctrl-C で取りやめる。Windows では、コードページによらないように `ReadConsoleW` で UTF-16 のまま読んで UTF-8 にする。
- スクリプトから動かすときのために、`--passphrase-file` でファイルの1行目をパスフレーズにできる。環境変数では受け取らない。子プロセスに引き継がれたり、ログに残ったりしやすいためである。
- ファイルは age 形式で、パスフレーズを scrypt（書くときは 2^18、読むときは 2^22 まで）で鍵にする。age のうち、パスフレーズで鍵を包む部分だけを自分で書いている。age のクレートは依存が約180増えるためである。C2SP の公式テストベクターで照合している。
- 中身は、秘密1つにつき `キー: 値` の行のまとまりにしたテキストである。復号したバッファから参照で切り出し、ニーモニックと秘密鍵は 0 で上書きする型に直接読む。書くときは、先に全体の長さを数えて確保し、バッファが伸びて古い領域が消されずに残ることを避ける。
- `heika wallet add` は、ニーモニックか秘密鍵を乱数から作り、ファイルにも画面にも出さずにそのままキーストアに入れる。`heika key mnemonic` で作ってから取り込むと、平文のファイルが一度ディスクに書かれ、消しても領域に残りうるためである。控えが要るときは、`heika wallet export` で書き出すか、`age -d` で開いて見る。
- ニーモニックは単語のまま入れ、空のパスフレーズで計算したシードは入れない。あとから BIP39 のパスフレーズで別の鍵を導出できるようにするためである。
- 書くときは、同じフォルダーの一時ファイルに書いて同期し、読み戻して同じパスフレーズで開けることを確かめてから置き換え、フォルダーも同期する。前のファイルは `.bak` に1つ残す。どこで落ちても、古いか新しいかのどちらかが完全な形で残る。Unix では、ファイルは 0600、フォルダーは 0700 で作る。
- `.bak` には1つ前の中身が残るので、キーストアからアカウントを消しても、`.bak` を消すまでは残る。
- `--expert` で聞く BIP39 のパスフレーズは、どこにも保存しない。保存すると、隠しウォレットがあることがキーストアからわかってしまうためである。空なら、公式ウォレットと同じ鍵になる。毎回聞くので、聞かれたこと自体からは、隠しウォレットを使ったかどうかはわからない。
- age の形式は否認できるものではない。見ればパスフレーズで暗号化したファイルだとわかり、違うパスフレーズは違うと判定される。否認できるのは、BIP39 のパスフレーズで導出する隠しウォレットのほうである。

## 対応していないこと

- Unix 以外では、書き出すファイルの権限を絞れない。Windows では置いたフォルダーの権限を引き継ぐ。Unix と Windows のほかでは、標準入力のバッファも避けられない。ビルド時に警告を出す。
- `mlock` などでスワップやコアダンプへの書き出しは防いでいない。
