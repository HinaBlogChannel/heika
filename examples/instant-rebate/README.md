# 即時還元

委任してくれた人のブロックの中で、そのブロックで受取先に入る分の一部を、その人に返すノードです。heika をライブラリとして使い、ブロックの中身に手を入れる例でもあります。

還元ノードは、ふつうは受取先の分をためておき、あとでまとめて委任してくれた人に払います。それまでは、ノードが委任してくれた人に借りがある状態です。ここでは、還元を報酬と同じブロックに入れるので、借りがたまりません。委任してくれた人は、自分の鍵で作られたブロックを見れば、還元が入っているかを 1 つずつ確かめられます。

ノードはいつでも還元をやめられるので、トラストレスではありません。やめたら、その場で見えます。

## 動かす

```sh
cargo build --release
./target/release/instant-rebate peer.yaml beneficiary.key 500
```

- `peer.yaml` は `heika experimental peer start` と同じ設定です。`beneficiary` を、受取先の鍵のアドレスにします
- `beneficiary.key` は受取先の秘密鍵のファイルです（PEM、DER、16進のどれでも）。ノードに置きっぱなしになるので、置いておく残高は少しにしてください
- `500` は返す千分率です（500 なら受取先の分の半分）

還元を入れるたびに、高さ、額、転送のハッシュを出します。

```
高さ 2 に還元 12.500000 XYM を入れます（…）
```

## 還元のしくみ

- **額:** そのブロックの手数料の合計にインフレを足し、受取先の割合（メインネットは 25%）を掛けたものの、決めた千分率です。還元の転送そのものの手数料も、合計に入れて求めます
- **宛先:** ブロックに署名した鍵がリモートなら、リンクしたメインのアカウントです。報酬を受け取るのと同じアカウントです
- **期限:** 転送の期限を、ブロックの時刻にします。ほかの人のブロックには入らず、ブロックが巻き戻れば、還元も入れ直されずに消えます
- **払う元手:** 報酬は、ブロックのトランザクションを当てたあとに入ります。還元は受取先の手持ちから先に払い、同じブロックの最後に入る受取先の分で埋まります。受取先には、1 ブロック分の還元より多い残高が要ります。足りなければ、ノードはそのブロックを還元なしで作ります
- **返さないブロック:** 受取先がほかのアドレスのブロック、受取先の分がないブロック、受取先が自分でハーベストしたブロック

## ライブラリとして使う

heika のノードは、ブロックを作るときに、未承認のトランザクションから手数料で選んだものを [`Assemble`](../../crates/heika-chain/src/produce.rs) に渡します。`Assemble` は、入れるもの（入れる順）を返します。足しても、外しても、並べ替えてもかまいません。ハーベストの当たりの確かめ、ブロックの署名、送る前の確かめは中核がします。

この例では `src/lib.rs` が `Assemble` の実装で、`src/main.rs` がそれをノードに渡して動かすだけのバイナリです。

### 渡されるもの

`Assemble::assemble` には、組む前に決まっていること（[`Slot`](../../crates/heika-chain/src/produce.rs)）と、選んだトランザクションのバイト列が渡ります。

| `Slot` の欄 | 中身 |
|---|---|
| `height`、`timestamp` | 作るブロックの高さと時刻（Nemesis からのミリ秒） |
| `signer` | ブロックに署名する鍵の公開鍵。委任ならリモートの鍵 |
| `harvester` | 報酬を受け取るアカウント。リモートなら、リンクしたメインのアカウント |
| `beneficiary` | 受取先 |
| `fee_multiplier` | ブロックの手数料の倍率。足したトランザクションも、この倍率で手数料を取られる |
| `inflation` | この高さのインフレの額 |
| `beneficiary_percentage` | 受取先の割合。署名した鍵のアドレスが受取先と同じなら 0 |

`Slot::beneficiary_amount(&transactions)` は、そのトランザクションを入れたときに受取先に入る額を返します。catapult の `HarvestFeeObserver` と同じ計算です。

### 最小の形

自分のトランザクションを先頭に足すだけなら、こうなります。

```rust
use std::sync::Arc;

use heika_chain::produce::{Assemble, Slot};

struct Prepend;

impl Assemble for Prepend {
    fn assemble(&self, slot: &Slot, chosen: Vec<Vec<u8>>) -> Vec<Vec<u8>> {
        // slot を見て、署名したトランザクションを作る。入れないなら chosen をそのまま返す
        let Some(mine) = build_and_sign(slot) else {
            return chosen;
        };
        std::iter::once(mine).chain(chosen).collect()
    }
}

heika_node::driver::run_with_assemble(&manifest, &stopping, &memory, Arc::new(Prepend))?;
```

- 設定の読み方とシグナルの受け方は、`src/main.rs` を見てください。`heika experimental peer start` と同じことをしています
- 署名に要るネットワークの定数（generation hash seed など）は、`heika_node::driver::network_parameters(&manifest.spec)` で引けます。プライベートなネットワークなら、設定の `network.resources` から読みます
- heika は crates.io に出していません。リポジトリの外から使うなら、リリースのタグで git に依存します。`Assemble` は v0.11.0 から入っています。そのタグの API の文書は、[Pages](https://hinablogchannel.github.io/heika/crates/) にあります

  ```toml
  [dependencies]
  heika-chain = { git = "https://github.com/HinaBlogChannel/heika", tag = "v0.13.0" }
  heika-node = { git = "https://github.com/HinaBlogChannel/heika", tag = "v0.13.0" }
  ```

  タグを付けないと master に依存することになり、文書とずれます

### 守ること

- **速く返す:** ブロックを作る流れの中で、そのまま呼びます。ネットワークやディスクを待つと、当たりの時刻に遅れます。要るものは先に用意しておいてください
- **何度呼ばれてもいいようにする:** 選んだトランザクションが弾かれると、中核はそれを外して選び直し、もう一度呼びます。同じ高さで何度も呼ばれますし、呼んだブロックが作られないこともあります。呼ばれたことを「ブロックに入った」とは数えないでください
- **入ったかはチェーンで見る:** 返したものがブロックに入ったか、そのブロックが残ったかは、チェーンを見て確かめます。この例のように期限をブロックの時刻にすると、巻き戻ったブロックのものは消えます
- **署名して返す:** 返すのは署名したトランザクションです。手数料は大きさ × `fee_multiplier` 以上にします。ブロックの件数の上限にも数えます
- **弾かれたら口なしで作り直す:** 足したものが確かめで弾かれたら、そのブロックは口を使わずに、選んだものだけで作り直します。そのブロックの間、口の変更はなかったことになります
- **ハーベストの鍵は渡らない:** 口に渡るのは、決まったことと選んだトランザクションだけです。自分のトランザクションに署名する鍵は、口の側で持ちます
- **ノードのローカルな決まり:** ここで決めることは、合意の規則ではありません。作ったブロックは、catapult がふつうに受け入れる形のままです

### ほかの使い道

- **委任してくれた人の手数料を 0 にする:** 委任してくれた人の、手数料 0 のトランザクションだけを入れたブロックにする。手数料の倍率はブロックごとなので、倍率 0 のブロックにすることになる（今の `Slot` では倍率を変えられないので、口を広げる必要がある）
- **並べ方を変える:** 手数料の順ではなく、受け取った順や、ハッシュの順に並べる
- **入れないものを決める:** 決めたアドレスのトランザクションを入れない、決めた種類だけを入れる

## プライベートネットで確かめたこと

2026-10-24 に、catapult 2 台と、この例のノード 1 台のプライベートネットで動かしました。インフレは 1 ブロック 100 XYM、返すのは 500‰ にしました。

- catapult が、還元の入ったブロックを受け入れた
- ハーベストした人の残高は、鎖に残ったブロックごとに 70 + 12.5 XYM、受取先は 25 − 12.5 XYM ずつ増えた
- catapult のブロックに枝を取り替えられたとき（深さ 1 と 2）、取り替えられたブロックの還元は、新しい枝にも未承認のトランザクションにも戻らなかった
