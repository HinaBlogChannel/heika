# GPU で探すアドレス

アドレスが `NAKAMOTO…` のように好きな文字で始まる（か、好きな文字を含む）秘密鍵を、GPU で探す例です。

鍵を作ってアドレスにするところは、heika-core をそのまま GPU の上で動かします。heika-core は std なしでも使えるように書いてあるので、Rust の `nvptx64-nvidia-cuda` ターゲットで NVIDIA の GPU 向けの PTX にでき、中身を書き直さずにカーネルになります。

## 動かす

カーネルは nightly で PTX にして、手元の側に埋め込みます。手元の側は stable でビルドできます。

```sh
rustup +nightly target add nvptx64-nvidia-cuda
rustup +nightly component add llvm-bitcode-linker llvm-tools
cargo +nightly build --release -p vanitygen-kernel --target nvptx64-nvidia-cuda
cargo build --release
./target/release/vanitygen-nvptx NAKAMO nakamo.key
```

- 1 つめの引数が模様、2 つめが秘密鍵を書くファイルです。ファイルは見つかってから作り、すでにあれば上書きしません。自分だけが読み書きできるように作ります
- 動かすマシンには NVIDIA のドライバー（`libcuda`）が要ります。ビルドには CUDA は要りません。見つかった GPU はすべて使います
- `--cpu` を付けると、GPU を使わず CPU のコアの数だけのスレッドで探します。GPU のないところで試すときや、速さをくらべるときに使います。`--no-default-features` でビルドすれば、PTX なしで `--cpu` だけのものができます

```
ざっと 4194304 回に 1 回当たります
GPU 0: NVIDIA …（SM … 個）
GPU 0: 256 スレッドのブロックを … 個ずつ起動します（1 スレッドのレジスター … 個）
GPU 0: 1 スレッドが … 個ずつ試します（1 回 … ミリ秒）
… 回（毎秒 … 回）
…
… 秒で見つかりました
アドレス: NAKAMO…
公開鍵: …
秘密鍵を nakamo.key に書きました
```

## 模様

| 書き方 | 意味 |
|---|---|
| `NAKAMOTO` | `NAKAMOTO` で始まる。末尾に `.*` を付けても同じ |
| `N.SUNBORU` | 2 文字目は何でもよく、3 文字目から `SUNBORU` |
| `N.*SUNBORU` | どこかに `SUNBORU` を含む |
| `NA.*SUNBORU` | `NA` で始まり、そのあとのどこかに `SUNBORU` を含む |

- 1 文字目は `N`（メインネット）か `T`（テストネット）で、どちらのアドレスを探すかもこれで決まります
- 文字は Base32 の `A`〜`Z` と `2`〜`7` です。`0`、`1`、`8`、`9` はアドレスに出てきません。小文字は大文字として読みます
- **2 文字目は `A`〜`D` のどれかにしかなりません。** アドレスの先頭の 1 バイトはネットワークで決まっていて（メインネットは `0x68`）、2 文字目の 5 ビットのうち 3 ビットがそこにかかるからです。`NSUNBORU` のような、ないアドレスの模様は、探し始める前に弾きます
- 39 文字目も、24 バイトの後ろの詰め物にかかるので、`A`、`I`、`Q`、`Y` のどれかにしかなりません

1 文字増えるごとに、かかる時間はおよそ 32 倍になります。始めに「ざっと何回に 1 回当たるか」を出すので、それと 5 秒ごとに出る速さから、どれくらいかかるかを見積もれます。

手元で測ったところ、GPU で探すと、同じマシンの CPU で探す（`--cpu`）より 80 倍ほど速くなりました。

## しくみ

### 候補の鍵

候補の秘密鍵は、OS の乱数で作った 32 バイトの種の先頭 8 バイトに、通し番号を XOR したものです。Symbol は秘密鍵を SHA-512 にかけてから使うので、番号が隣どうしの鍵でも、鍵としては関係がありません。

- GPU には種と模様を渡し、当たった**番号だけ**を返してもらいます。秘密鍵そのものは GPU から出てきません
- 手元の側は、番号から鍵を作り直し、アドレスが模様に合うことを確かめてからファイルに書きます。GPU の答えをうのみにしません
- 探し終えたら、GPU のメモリの種を 0 で消します

種を短くしてはいけません。Ethereum の vanitygen の Profanity は、種が 32 ビットしかなかったために、見つけたアドレスの公開鍵から秘密鍵を逆算され、大きなお金が盗まれました。ここでは種を 256 ビットにしています。

### カーネル

`kernel` の `search` が、GPU の 1 スレッドで動く部分です。やっていることは CPU で 1 個の鍵を試すときと同じで、heika-core の関数を呼ぶだけです。

```rust
let key = candidate(seed, counter);
let address = Address::from_public_key(&PublicKey::from_private_key(&key), network);
if pattern.matches(&address.0) { /* 番号を返す */ }
```

- `Pattern` は `repr(C)` で、手元で読んだものをそのままのバイト列で GPU に渡します
- 照合は、アドレスを Base32 の文字列にせず、24 バイトから 5 ビットずつ取り出して比べます
- ブロックの大きさと数は、カーネルのレジスターの使い方とカードから、いちばん埋まるものをドライバーに決めてもらいます（`cuOccupancyMaxPotentialBlockSize`）
- 1 スレッドが 1 回の起動で試す数は、1 から始めて、1 回の起動が 100 ミリ秒前後になるまで倍にしていきます。カードごとに違う値に落ち着きます。画面を出している GPU で 1 回の起動が長すぎると、画面が固まったり、ウォッチドッグに止められたりするので、短く刻みます
- heika-core は `alloc` を使うのでアロケーターが要りますが、鍵からアドレスを作る道筋では割り当てません。GPU 向けには、割り当てようとしたら失敗するものを置いています

### 先頭だけなら、もっと削れる

アドレスの 24 バイトは、ネットワークの 1 バイト、公開鍵のハッシュの 20 バイト、チェックサムの 3 バイトです。チェックサムは、前の 21 バイトをもう一度 SHA3-256 にかけて作ります。

先頭の模様は、たいていハッシュの 20 バイトの中で決まるので、本当はチェックサムの SHA3 は当たったときだけ計算すれば足ります。ここでは heika-core の `Address::from_public_key` をそのまま使っているので、毎回計算しています。後ろの 5 文字ほどはチェックサムにかかるので、`N.*SUNBORU` のような含む模様では、この計算がちゃんと要ります。
