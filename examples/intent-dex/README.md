# 預けない交換

モザイクどうしを、誰にも預けずに交換する例です。注文は署名済みのトランザクションとしてチェーンに出し、約定させるのはブロックを作るハーベスターです。Symbol の規則は変えないので、catapult もそのまま受け入れます。heika をライブラリとして使い、ブロックの中身に手を入れる例でもあります。

Symbol にはスマートコントラクトがないので、ふつうは「1 つのトランザクションの中で交換を閉じる」ことを考えます。でもアグリゲートの署名は中身全体にかかるので、相手のアドレスを決めないと注文に署名できません。ここでは、1 つのトランザクションではなく、**ハーベスターが並べる 1 つのブロック**を交換の単位にします。ブロックの中の並びはハーベスターが決めるので、ほかの人はそのあいだに割り込めません。

試作です。プライベートネットで、注文の約定と、約定できない注文を外すところまで確かめました（下の「プライベートネットで確かめたこと」）。

## 動かす

```sh
cargo build --release
B=./target/release/intent-dex
$B board peer.yaml                                         # 掲示板のアドレス
$B mint  peer.yaml maker.key 1000000                       # 試すためのモザイクを作る
$B order peer.yaml maker.key 0D7D188F015BEBB2:50 xym:1000000000 100000
$B solve peer.yaml desk.key 0D7D188F015BEBB2 xym 1/20000000 10000000000
```

- `peer.yaml` は `heika experimental peer start` と同じ設定です。どのサブコマンドも、ここからネットワークと REST（最初の `rest` の口）を決めます。`solve` は、このノードそのものとして動きます。掲示板を読むので、`storage.search` に `transactions` を入れてください
- 鍵のファイルは PEM、DER、16進のどれでも読みます
- モザイクは 16 進の ID か `xym` で、量は最小単位で書きます
- `order`: `maker.key` の人が、TOKEN を 50 出して 1000 XYM を受け取り、約定させた人に 0.1 XYM 払う注文を出します。期限は 2 時間です
- `solve`: `desk.key` の在庫で、TOKEN を受け取って XYM を出します。XYM 20,000,000（20 XYM）ごとに TOKEN 1 以上、1 回に 10,000 XYM までです。在庫の鍵はノードに置きっぱなしになるので、ハーベストの鍵とは分け、置く残高は少しにしてください

約定させるたびに、高さと注文を出します。

```
高さ 38 で注文 … を約定させます（0D7D188F015BEBB2 を 50 受け取り、178CE294F0E07B44 を 1000000000 出す）
```

## 交換のしくみ

### 注文

メイカーは注文ごとに、ランダムな鍵 P を作ります。そして、次の 3 つを入れた AggregateComplete に署名します。

1. メイカー → P に、出すもの
2. P → メイカーに、欲しいもの
3. メイカー → P に、約定させた人への手数料の XYM

P の秘密鍵は、注文と一緒に公開します。なので、P の連署は誰でも付けられます。相手が決まっていない注文に、前もって署名できるのはこのためです。

注文は、[`board`](src/lib.rs) のアドレスあての送金のメッセージに入れて出します。メッセージは、頭の 4 バイト `D3 49 44 58`、版の 1 バイト、P の秘密鍵の 32 バイト、署名した注文のバイト列です。モザイク 1 種類どうしなら約 490 バイトで、メッセージの上限（1023 バイト）に収まります。掲示板のアドレスは、決まった文字列の SHA3-256 を公開鍵とみなして作ります。対になる秘密鍵は誰も知らないので、受け取りの制限をかけて掲示板を止められる人もいません。AggregateComplete なので、ハッシュロックは要りません。

### 約定

ハーベスターは、自分のブロックに次の 3 つを続けて並べます。

1. 在庫 → P に、メイカーが欲しいもの（貸す）
2. 注文。ここで P の連署を付ける
3. P → 在庫に、メイカーが出したものと、手数料の XYM の残り（回収する）

ブロックは、中のトランザクションが順に全部通らないと無効になります。そして、並びはハーベスターが決めます。なので、P に置いたものを、そのあいだに誰かに抜かれることはありません。

- **メイカーは誰も信じなくていい:** 注文は署名したとおりにしか動きません
- **ハーベスターも誰も信じなくていい:** 自分で組んで確かめたブロックを出すだけです
- **在庫を出すのは、ブロックを作るハーベスター本人:** ほかの人が在庫を出すなら、ハーベスターが「貸す」だけを入れて残りを入れないことを、信じなければなりません
- 1 → 2 → 3 は 1 つのブロックの中で何度でも繰り返せるので、在庫は、いちばん大きい 1 回分の額があれば足ります

### 取り消しと乗っ取り

- メイカーが取り消すには、期限を待つか、出すものをよそに動かします。残高が足りなくなれば、注文は通りません
- P の鍵は公開なので、誰でも P をマルチシグにしたり、制限をかけたりして、その注文を通らなくできます。ただし、盗むことはできません。P は注文ごとに変わるので、取り消すには注文の数だけ手数料がかかります
- 前もって P を守る手はありません。操作の制限を変えるトランザクションそのものは禁止できず（catapult の `AccountOperationRestrictionNoSelfBlocking`）、マルチシグのしきい値を変えるだけの変更は minApproval で通るからです（`MultisigAggregateSufficientCosignatoriesValidator`）

### この試作で割り切ったこと

- 約定させられるのは、ノードの在庫で相手になる注文だけです。逆向きの注文どうしを突き合わせるのは、まだ作っていません
- 全部約定するか、何もしないかです。一部だけは約定させられません
- 1 つのブロックに約定させるのは 1 つの注文だけです。弾かれたときに、ほかの注文まで巻き込まないようにするためです
- 約定できる注文かは、10 秒ごとに掲示板を読み直すときに、REST で確かめます（期限、もう約定していないか、P がマルチシグや制限で乗っ取られていないか）。残高までは見ません。通らなかったものは、3 つの高さで試したらあきらめます
- 約定させられるのは、この作りのハーベスターだけです。catapult のハーベスターがブロックを作る番では、約定しません

## ライブラリとして使う

heika のノードは、ブロックを作るときに、未承認のトランザクションから手数料で選んだものを [`Assemble`](../../crates/heika-chain/src/produce.rs) に渡します。`Assemble` は、入れるもの（入れる順）を返します。足しても、外しても、並べ替えてもかまいません。ハーベストの当たりの確かめ、ブロックの署名、送る前の確かめは中核がします。`Assemble` の決まりは、[即時還元の README](../instant-rebate/README.md#ライブラリとして使う) にまとめてあります。

この例では、`src/lib.rs` に注文の形（`Order`）、約定の組み方（`Desk::fill`）、`Assemble` の実装（`Solver`）があります。`src/main.rs` は、それをノードに渡し、掲示板を読み直すスレッドを動かすバイナリです。

### 最小の形

ブロックの中で、自分のトランザクションで他人のトランザクションを挟むと、こうなります。

```rust
use std::sync::Arc;

use heika_chain::produce::{Assemble, Slot};

struct Sandwich;

impl Assemble for Sandwich {
    fn assemble(&self, slot: &Slot, chosen: Vec<Vec<u8>>) -> Vec<Vec<u8>> {
        // 前に用意しておいたものから、今のブロックで通るものを選ぶ。ネットワークは待たない
        let Some([before, theirs, after]) = pick(slot) else {
            return chosen;
        };
        [before, theirs, after].into_iter().chain(chosen).collect()
    }
}

heika_node::driver::run_with_assemble(&manifest, &stopping, &memory, Arc::new(Sandwich))?;
```

### 気をつけること

- **最大手数料とブロックの倍率:** ブロックの手数料の倍率は、選んだトランザクションの倍率のいちばん低いものです（[`choose`](../../crates/heika-chain/src/produce.rs)。メムプールが空なら 0）。他人の署名済みのトランザクションは最大手数料を変えられないので、`slot.fee_multiplier` で足りるかを先に確かめます。足したトランザクションの手数料は、大きさ × `slot.fee_multiplier` にします
- **連署を付けると大きさが変わる:** 連署 1 つで 104 バイト増えます。署名する側は、連署の分も見込んで最大手数料を決めます（`Transaction::fee_for` の 2 つ目の引数）
- **期限はブロックの時刻に:** 貸すと回収するの期限をブロックの時刻にしておけば、ブロックが巻き戻っても、ほかの人のブロックに入りません。注文のほうは期限が長いので、巻き戻ったあとでメムプールに戻ることがあります。でも、P に貸すものがなければ通らないので、メイカーが損をすることはありません
- **弾かれたことは知らされない:** 返したものが弾かれると、中核はそのブロックを口なしで作り直します（ログに「直したトランザクションが弾かれたので、直す前のもので作ります」と出ます）。口の側には知らされないので、何度試したかは自分で数えます。同じ高さで何度も呼ばれることもあるので、数えるのは高さごとです
- **状態は前に見ておく:** `assemble` の中からは状態を引けません。残高や乗っ取りは、別のスレッドで REST に聞いておきます

### ほかの使い道

- **逆向きの注文どうしを突き合わせる:** 在庫で貸すのは同じで、注文 A と注文 B を続けて並べます。在庫は行き来するだけで、値段の差がハーベストした人に残ります
- **ブロックごとのオークション:** そのブロックで約定させる注文を、値段の順に全部集めて、同じ値段でまとめて約定させる
- **一度だけの約束ごと:** 「P と公開の鍵」の形は、交換に限りません。誰が相手でもいい約束（先着 1 名への支払いなど）を、署名済みで置いておけます

## プライベートネットで確かめたこと

2026-10-25 に、catapult 2 台と、この例のノード 1 台（投票もする）のプライベートネットで動かしました。ブロックの間隔は 5 秒です。

- 掲示板に出した注文を拾い、高さ 38 で約定させた。そのブロックは、貸す（送金）、注文（P の連署付きのアグリゲート）、回収する（送金）の 3 つだった
- catapult の 2 台が、そのブロックを受け入れた。そのあとも、heika と同じハッシュで進んだ
- メイカーは TOKEN が 50 減り、1000 XYM から手数料の 0.1 XYM を引いた分が増えた。在庫は TOKEN が 50 増え、XYM が 999.9 減った（ブロックの倍率が 0 だったので、回収の手数料は 0）。P には何も残らなかった
- 持っている量より多く出す注文は、高さ 61、62、63 で試すと、どれも弾かれて口なしで作り直された。そのあとは試さず、チェーンもファイナライズも止まらなかった

確かめていないこと:

- P をマルチシグにしたり制限をかけたりした注文を、外すところ（掲示板を読み直すときに REST で見ていますが、プライベートネットでは試していません）
- catapult のブロックに枝を取り替えられたとき
