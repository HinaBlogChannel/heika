# XYM を EVM に持っていく橋

Symbol の XYM を預かって、EVM のチェーンに同じ量の wXYM を発行する例です。wXYM を燃やすと、預かっていた XYM を Symbol に返します。

預かるのも発行するのも、見張り役みんなで分けて持つ鍵の、**署名 1 つ**で認めます。

- Symbol の側：預かり口座は、見張り役のグループ鍵（Ed25519）だけを連署者にしたマルチシグです
- EVM の側：wXYM のコントラクトは、見張り役のグループ鍵（secp256k1）の Schnorr の署名を 1 つ確かめます。見張り役が何人いても、ガスは同じです

どちらの鍵も FROST で分けて持ち、ROAST（[examples/roast](../roast)）で署名します。見張り役の誰かが黙っていても、署名できます。

試作です。見張り役はみなこのプロセスの中にいて、鍵を配るのもこのプロセス（ディーラー）です。EVM は手元の anvil です。本物の資産を預けるものではありません。

## 動かす

要るもの：

- Symbol のノードの REST。heika のノードなら、設定に検索表 `storage.search: [Transactions]` を入れておきます（入金と引き出しを検索で探すため）
- EVM のノード。ここでは [Foundry](https://getfoundry.sh/) の `anvil` を使います。コントラクトのビルドに `forge` も使います

```sh
(cd contracts && forge build)
cargo build --release
anvil --port 18545 &
./target/release/evm-bridge run peer.yaml http://127.0.0.1:18545
```

- `peer.yaml` は `heika experimental peer start` と同じ設定です。ここからネットワークと REST（最初の `rest` の口）を決めます
- 量は XYM の最小単位で書きます（1000000 で 1 XYM）

起動すると、見張り役に鍵を配り、預かり口座のアドレスを出して、手数料の予算（20 XYM）が届くのを待ちます。届いたら預かり口座をマルチシグにして、anvil に wXYM を置きます。

```
見張り役 5 人に鍵を配りました（署名に要るのは 3 人。5 人目はずっと黙っています）
預かり口座: T…
このアドレスに 20.000000 XYM 以上を送ってください。届くのを待ちます
高さ 10 で、預かり口座を見張り役の鍵だけで動かせるようにしました（預かり口座の鍵は捨てました）
wXYM: 0x…
入金するときは、メッセージに発行先の EVM のアドレス（0x…）を書いてください
見張り役を入れ替えるときは、rotate と打ってください
```

### 入金して、発行してもらう

預かり口座に、メッセージに EVM のアドレスを書いて XYM を送ります。どのウォレットからでもかまいません。この例の `send` でも送れます（秘密鍵は標準入力から読みます）。

```sh
./target/release/evm-bridge send peer.yaml <預かり口座> 5000000 0x<EVM のアドレス> < 秘密鍵のファイル
```

入金がファイナライズされると、見張り役がその EVM のアドレスに wXYM を発行します。

```
高さ 11 の入金で、0x… に 5.000000 wXYM を発行しました
```

### 燃やして、Symbol に返してもらう

wXYM の `burn(量, Symbol のアドレス)` を呼びます。Symbol のアドレスは、24 バイトの生のアドレス（`bytes24`）で渡します。

```sh
cast send <wXYM> "burn(uint256,bytes24)" 2000000 0x<Symbol のアドレスの 16 進> --from <EVM のアドレス> --unlocked
```

見張り役が Burn を拾い、預かり口座から送ります。

```
Burn 0 の 2.000000 XYM を、高さ 24 で T… に送りました
```

### 見張り役を入れ替える

`rotate` と打つと、新しい見張り役に鍵を配り、両方のチェーンで鍵を差し替えます。預かった XYM と発行した wXYM は、そのままです。

```
新しい見張り役 5 人に鍵を配りました
wXYM の鍵を差し替えました
高さ 26 で、預かり口座の連署者を新しい鍵に差し替えました（預かった XYM は動かしていません）
```

## しくみ

### 預かり口座

預かり口座は、ふつうのアカウントとして作り、すぐに 1-of-1 のマルチシグに変えます。連署者は、見張り役のグループ鍵のアカウントだけです。

1. 使い捨ての鍵でアカウントを作り、手数料の予算を入れてもらう
2. その鍵で、アグリゲートに署名する。中身は 2 つ
   - 預かり口座から、グループ鍵のアカウントに手数料の予算を送る
   - 預かり口座を、グループ鍵を連署者にしたマルチシグにする
3. グループ鍵が、このアグリゲートに連署する（Symbol では、連署者に加わる側の同意が要る）
4. 使い捨ての鍵を捨てる

マルチシグになったアカウントは、自分の鍵では動かせません。預かった XYM を動かせるのは、連署者のグループ鍵だけです。

引き出しは、グループ鍵が署名するアグリゲートです。中身は、預かり口座から宛先への送金で、メッセージに Burn の番号（`burn:<番号>`）を入れます。手数料は、アグリゲートに署名するグループ鍵のアカウントが、予算から払います。

### 発行

見張り役は、預かり口座への送金を検索し、**ファイナライズされたものだけ**を拾います。ロールバックで消えるかもしれない入金に、発行しないためです。

発行に署名するのは、`keccak256(abi.encode("mint", chainid, コントラクト, 宛先, 量, 入金のハッシュ))` です。チェーンとコントラクトを入れるので、ほかのチェーンやコントラクトでは使い回せません。コントラクトは、発行に使った入金のハッシュを覚えておき、同じ入金では 2 回発行しません。

### EVM で Schnorr の署名を確かめる

FROST の secp256k1 の署名は、Schnorr の署名 (R, z) です。z·G = R + e·P なら正しい署名です（P はグループ鍵、e はチャレンジのハッシュ）。

EVM には楕円曲線の掛け算がないので、[`FrostSecp256k1.sol`](contracts/src/FrostSecp256k1.sol) は ecrecover に計算を肩代わりさせます。

- ecrecover(h, v, r, s) は、x 座標が r の点 X について、r⁻¹·(s·X − h·G) のアドレスを返す
- X = P、h = −z·Px、s = −e·Px とすると、返ってくるのは z·G − e·P のアドレス
- それが R のアドレスと同じなら、署名は正しい

チャレンジ e は、RFC 9591 の FROST(secp256k1, SHA-256) と同じく、RFC 9380 の expand_message_xmd（SHA-256）で作ります。SHA-256 は EVM のプリコンパイルにあります。1 回確かめるのにかかるガスは、約 1.3 万です。

### 引き出しを 2 回払わない

Symbol のトランザクションには期限があります（この例では 1 時間）。引き出しが期限までに承認されなかったら、作り直して出し直します。

ただし、前に出したものが期限までに承認されるかもしれません。両方が承認されると、2 回払うことになります。なので、**前の引き出しの期限が過ぎるまでは、出し直しません**。期限が過ぎたら、預かり口座から出た送金のメッセージを検索して、その Burn がもう払われていないかを確かめてから出し直します。

### 見張り役の入れ替え

見張り役が入れ替わると、グループ鍵も変わります。

- EVM の側：今のグループ鍵で「この鍵に差し替える」に署名し、コントラクトの鍵を差し替えます。署名するものには、差し替えた回数を入れて、使い回せないようにします
- Symbol の側：今のグループ鍵が署名するアグリゲートで、預かり口座の連署者を新しいグループ鍵に入れ替えます。新しいグループ鍵が連署して、加わることに同意します。手数料の予算も、新しいグループ鍵のアカウントに移します

公開鍵が変わっても困らないので、分け前を配り直す難しい仕組み（resharing）は要りません。Symbol のマルチシグのおかげです。分け前を定期的に作り直すだけなら、公開鍵を変えない `frost_core::keys::refresh` も使えます。

## 信じているもの

- **見張り役の多数が正直であること**。署名に要る数（この例では 5 人のうち 3 人）の見張り役が組めば、預かった XYM を好きなところに送れます。Liquid のフェデレーションなどと同じ立ち位置です
- **見張り役が見ているノード**。見張り役は、自分のノードの REST と EVM の RPC を信じます。どのノードを見るかは、見張り役それぞれの責任です。同じノードにみんなで頼らないことが大事です
  - Symbol の側は、自分の heika のノードを立てれば、ファイナライズまで自分で確かめられます
  - EVM の側の RPC が本当のことを言っているかは、heika では確かめません。heika は Symbol のツールキットで、EVM のチェーンを確かめるのは heika の責務の外です。EVM のノードを自分で立てるか、軽量クライアントを使うかは、見張り役が選びます

不正をした見張り役を罰する仕組み（スラッシング）はありません。

- Symbol には、担保を自動で取り上げる仕組みがない
- しきい値の署名は、ふつうの署名 1 つになるので、誰が署名に加わったかがわからない
- EVM で Symbol の不正を確かめるには、Ed25519 と SHA3-256（EVM の Keccak-256 とは別物）を Solidity で書くことになり、重い

## やっていないこと

- **ディーラーなしで鍵を作る（DKG）**。今はディーラーが配っていて、配る前の一瞬だけ鍵の全体を知っています。次は `frost_core::keys::dkg` を、Symbol のメッセージ（約束の値は平文、分け前は暗号化）でやりとりして回します
- **本物の EVM のネット**。トランザクションは、anvil の開発用のアカウントに署名してもらっています（`eth_sendTransaction`）。本物のネットでは、自分で署名して `eth_sendRawTransaction` で送ります
- **宛先の確かめ**。メッセージに EVM のアドレスがない入金は、発行されずに預かり口座に残ります。Burn の宛先がほかのネットワークのアドレスなら、払えません（wXYM はもう燃えています）
- **crypto-bigint の勧告（RUSTSEC-2026-0387）**。EVM の側の鍵（secp256k1）の計算に使う `frost-secp256k1` 3.0.0 は `k256` 0.13 を使い、その下の `crypto-bigint` 0.5 系には、一定時間で動くはずの計算が秘密の値で分岐することがある、という勧告が出ています。直った版は 0.7.6 以上だけで、`k256` 0.14 系に移れば入ります。`frost-secp256k1` が新しい `k256` に移るまでは、この例は古いままです。見張り役の処理時間を細かく測れる相手がいると、分け前を推し量られるおそれがあります。heika の本体と、ほかの例は `crypto-bigint` を使っていません
- **再起動**。見張り役の鍵も、どこまで見たかも、メモリにしかありません。止めたら、預かり口座ごと作り直しです

## プライベートネットで確かめたこと

2026-10-29 に、heika 4 台（ハーベストと投票をする 3 台と、見るだけの 1 台）のプライベートネットと anvil で動かしました。見張り役は 5 人で、署名に要るのは 3 人、1 人はずっと黙っています。

- 預かり口座を作った（高さ 10）。預かり口座の鍵で署名し、グループ鍵が連署したアグリゲートが通った
- 5 XYM の入金（高さ 11）が、ファイナライズされたあとに 5 wXYM になった
- 2 wXYM を燃やすと、預かり口座から 2 XYM が出た（高さ 24）
- 見張り役を入れ替えた。wXYM の鍵を差し替え、預かり口座の連署者を新しいグループ鍵にした（高さ 26）
- 入れ替えたあとも、新しい見張り役で発行（高さ 27 の入金）と引き出し（高さ 28）ができた
- 4 台とも、同じブロックと同じ預かり口座の残高になった

ブロックを作ったのも署名を確かめたのも heika です。catapult が同じものを受け付けるかは、まだ確かめていません。

最初に動かしたときは、heika のノードの不具合で、同じ引き出しがブロックに何度も入り直し、ノードどうしでチェーンが割れました（master の 7581374 で直しました）。

## heika の使い方

- 預かり口座、引き出し、入れ替えのトランザクションは、[`src/symbol.rs`](src/symbol.rs) の `setup`、`withdraw`、`rotate` で作ります。どれも `heika_transaction::Aggregate` の AggregateComplete です
  - 中のトランザクションは `EmbeddedTransaction::new(署名者, ネットワーク, 本体)` で作ります。預かり口座の送金やマルチシグの変更は、署名者を預かり口座にします
  - 手数料は `Transaction::fee_for(倍率, 連署の数)` で、あとから足す連署の分まで見込みます
- FROST の署名は、ふつうの Ed25519 の署名です
  - アグリゲートの署名：`Transaction::signing_payload` に署名して、`transaction.signature` に入れます
  - 連署：`Transaction::hash` に署名して、`Cosignature { signer_public_key, signature }` を作り、`Aggregate::add_cosignature` で足します。連署を足してもハッシュは変わりません
  - `Transaction::verify` と `Transaction::verify_cosignatures` で、出す前に確かめられます
- 入金は `GET /transactions/confirmed?recipientAddress=…&type=16724&fromHeight=…&toHeight=…` で探します。`toHeight` に `/chain/info` の `latestFinalizedBlock.height` を入れると、ファイナライズされたものだけになります
- 払った引き出しは `GET /transactions/confirmed?signerPublicKey=<預かり口座の公開鍵>&embedded=true` で、アグリゲートの中の送金まで探します
