# Symbol の上の EVM

Symbol を掲示板にして、EVM を動かす例です。Symbol にハードフォークは要りません。

- EVM のトランザクションは、Symbol の転送のメッセージに入れて載せます
- 並び順は、Symbol のブロックの中の順です。別のシーケンサーはいません（based ordering）
- 実行するのは、このノードです。Symbol の確定したブロックまでを読めば、誰が実行しても同じ状態（同じ状態のルート）になります

データの置き場所と並び順と最終性は Symbol に任せ、どの状態が正しいかはロールアップの規則で決めます。こういうものを、ソブリンロールアップと呼びます。規則を変えたいときは、このノードを変えるだけで済みます。Symbol の許しは要りません。

外からは、ふつうの Ethereum の JSON-RPC に見えます。`cast` などで、送金もコントラクトのデプロイも呼び出しもできます。

試作です。ロールアップの中の ETH は genesis で配った分しかなく、外から持ち込むことも出すこともできません（ほかのチェーンとの橋はありません）。ガス代は、この ETH で払って燃やします。

## 動かす

要るもの：

- Symbol のノードの REST。heika のノードなら、設定に検索表 `storage.search: [Transactions]` を入れておきます（受け箱に載ったものを検索で探すため）
- Symbol に載せる係（リレー）の鍵と、手数料の XYM。読むだけのノードなら要りません
- 試すなら [Foundry](https://getfoundry.sh/) の `cast`

最初の状態を `genesis.json` に書きます。`alloc` は geth の genesis と同じ形で、残高（wei）、nonce、コード、ストレージを置けます。

```json
{
  "chainId": 31415,
  "start": 17588,
  "alloc": {
    "0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266": { "balance": "0x3635c9adc5dea00000" }
  }
}
```

- `chainId`：EVM のチェーン ID です。受け箱のアドレスも、ここから決まります
- `start`：この Symbol の高さの次のブロックから読みます。ロールアップを始めるときの、確定した高さにしておきます

```sh
cargo build --release
./target/release/evm-rollup run peer.yaml genesis.json 127.0.0.1:8545 relay.key
```

- `peer.yaml` は `heika experimental peer start` と同じ設定です。ここからネットワークと REST（最初の `rest` の口）を決めます
- `127.0.0.1:8545` で、JSON-RPC を受けます
- `relay.key` はリレーの秘密鍵のファイルです（PEM、DER、16 進のどれでも）。`eth_sendRawTransaction` で受け取ったものを、この鍵で Symbol に載せ、手数料も払います。なければ、読むだけのノードになります

ガスの値段は、`cast` が JSON-RPC で今の basefee を聞いて、自分で付けます。

```sh
cast send --rpc-url http://127.0.0.1:8545 --private-key $KEY 0x000000000000000000000000000000000000dEaD --value 1ether
```

Symbol に自分で載せたいときは、受け箱のアドレスを出して、そこに宛てます（[載せ方](#載せ方)）。

```sh
./target/release/evm-rollup inbox peer.yaml genesis.json
```

## しくみ

### 載せ方

- Symbol のトランザクション 1 つに、EVM のトランザクションを 1 つ入れます
- 宛先は、受け箱のアドレスです。チェーン ID から作ったハッシュを公開鍵の代わりにして作るので、誰も秘密鍵を持っていません
- メッセージは、先頭に `\0evm`（4 バイト）を付け、その後ろに EIP-2718 の形のバイト列を入れます。1 バイト目の 0 は平文のメッセージの印です
- 1 つのメッセージ（1 KB）に収まらなければ、アグリゲートの中の転送に分けます。最大でメッセージ 100 個、約 100 KB です。コントラクトのデプロイの上限（initcode 49,152 バイト）も収まります
- アグリゲートは全部入るか全部入らないかなので、途中の欠片だけが載ることはありません

誰が載せてもかまいません。EVM のトランザクションにはそれ自体に署名が入っているので、リレーが中身を変えることはできません。リレーに断られたら、自分で載せれば必ず入ります。

### 並び順と実行

- ロールアップのブロックは、Symbol のブロックと 1 対 1 で、高さも同じです。EVM のトランザクションがなければ空のブロックです
- ブロックの中の順に、1 件ずつ [revm](https://github.com/bluealloy/revm) で実行します
- 読めない、署名が合わない、チェーン ID が違う、nonce が合わない、などのものは、入らなかったことにします。レシートは出ません。誰が実行しても同じように外れます
- 署名と nonce が合っていれば、必ずレシートを出します。払えない（max fee が basefee に届かない、残高が足りない）などで実行できなければ、失敗（status 0、ガス 0）にして、nonce は使ったことにします。使う人にはすぐに失敗が見え、署名し直して送り直せます
- 同じものが 2 回載っても、2 回目は nonce が合わないので外れます
- blob 付きのトランザクション（type 3）は入れません。blob を置く層がないためです

### latest と finalized

ノードは状態を 2 つ持ちます。

- `finalized`：Symbol の確定したブロックまで。巻き戻りません。`safe` もこちらです
- `latest`：Symbol の先頭のブロックまで。`finalized` の写しに、確定していないブロックを毎回実行し直して作ります。Symbol で巻き戻りが起きても、次に作り直すときに直ります。`pending` もこちらです

送ったものは、Symbol のブロックに入れば `latest` に見えます。お金の受け渡しのように重いことをするときだけ、`finalized` を待ちます。

### ガス

- Symbol の XYM の手数料は大きさで決まり、計算の重さでは決まりません。計算の重さには、ロールアップの中の ETH で、EIP-1559 と同じく basefee を払ってもらい、燃やします
- basefee は、トランザクション 1 件ごとに決めます。1 秒あたり 100 万ガスの目標より多く使われると、超えた分がたまり、たまった分に応じて指数で上がります（EIP-4844 の blob の手数料と同じ式）。目標の 2 倍で使われ続けると、12 秒で約 12.5% 上がります。時間がたつと下がり、下限は 1 gwei です。時間は Symbol のブロックの時刻で測るので、誰が計算しても同じになります
- ブロックのガスの合計の上限はありません。同じ Symbol のブロックに入った人どうしで、枠を取り合いません。払える人は必ず実行され、払えない人は自分の分が失敗するだけです。ほかの人のせいで弾かれることはありません
- 1 件ごとの上限は、Ethereum と同じ 2^24（約 1680 万）ガスです
- 優先料（priority fee）は、ブロックの coinbase（0x0、誰も鍵を持たない）に入ります

### 状態のルート

Ethereum と同じ Merkle Patricia Trie で求めます。空の口座は入れません（EIP-161）。同じ最初の状態と同じトランザクションなら、anvil と同じルートになることを、テストで確かめています。

## 信じているもの

- **Symbol：** データがあること、並び順、最終性です。確定したブロックまでで状態を決めるので、Symbol の確定（ファイナライズの投票者）を信じることになります
- **読んでいる Symbol のノード：** 自分で動かしているノードなら、そのノードが確かめたものを読んでいるだけです。誰かのノードの REST を読むなら、そのノードを信じることになります
- **ハーベスター：** ブロックの中の順を決めるのはハーベスターなので、MEV（順番で得をすること）もハーベスターのものになります。based ordering の性質です

## やっていないこと

- **状態を保存しません。** 起動のたびに、`start` から読み直します
- **過去の高さの状態を持っていません。** 状態を引けるのは `latest` と `finalized` だけです
- **JSON-RPC は一部だけです。** `cast` で送金、デプロイ、呼び出しをするのに要るものだけです。`eth_getLogs` や `eth_getBlockByHash` などはありません。MetaMask などの wallet では試していません
- **ブロックのハッシュは、Symbol のブロックのハッシュではありません。** チェーン ID と高さと状態のルートから作ります。`PREVRANDAO` は 0 です
- **未承認のトランザクションを持ちません。** `pending` の nonce は、ブロックに入ったものまでです。続けて送るときは、前のものが入るのを待ってください
- **橋はありません。** Symbol の XYM をロールアップに持ち込むことも、出すこともできません
- **crypto-bigint の勧告（RUSTSEC-2026-0387）が残っています。** revm と alloy が使う `k256` 0.13 の下の `crypto-bigint` 0.5 系に、秘密の値で計算の時間が変わることがある、という勧告が出ています。このノードがその計算に使うのは、トランザクションの署名者を割り出すことと、precompile の計算だけで、どちらも公開されたデータです。時間を測られても、漏れるものはありません。秘密鍵で署名するのは `cast` などの側で、リレーの鍵は Symbol の Ed25519 です。CI の audit では、この例だけこの勧告を見逃しています

## プライベートネットで確かめたこと

2026-10-30 に、heika 4 台のプライベートネットで動かしました。リレーの鍵を持つノード 1 台と、読むだけのノード 1 台を立てました。

basefee を入れたあとに確かめたこと：

- 値段を付けずに `cast send` した送金に、`cast` が今の basefee（1 gwei）を付け、Symbol のブロックに入り、数秒で `latest` に見えた
- 値段 0 で送った送金は、失敗（status 0、ガス 0）のレシートが返り、nonce は進んだ
- Symbol で確定したあとの状態のルートが、2 台とも同じになった

basefee を入れる前（ガス代 0 で、ブロックのガスの合計に上限を置いていたころ）に確かめたこと。リレーの鍵を持つノードと、読むだけのノードに加えて、あとから 3 台目を起動しました：

- wXYM のコントラクト（[examples/evm-bridge](../evm-bridge)。initcode 8,276 バイト）のデプロイが、9 つのメッセージのアグリゲートに分かれて載り、デプロイされた
- 残高のない `burn` は、`cast estimate` では revert の理由付きで断られ、ガスを指定して送ると、失敗（status 0）として入った
- Symbol で確定したあとの状態のルートが、3 台とも同じになった。あとから起動した 3 台目も、`start` から読み直して同じルートになった

## heika の使い方

このノードは、heika のノードの REST を読むだけです。読むのに使っているのは、catapult の REST と同じ検索です。

- `GET /chain/info`：先頭の高さと、確定した高さ
- `GET /transactions/confirmed?recipientAddress=<受け箱>&type=16724&embedded=true&fromHeight=<から>&toHeight=<まで>&order=asc`：受け箱に宛てた転送を、高さ、ブロックの中の順、アグリゲートの中の順に。アグリゲートの中のものは、`meta.aggregateHash` で外側にまとめます
- `GET /blocks/{height}`：ブロックの時刻

この形のまま、実行する部分（`src/rollup.rs`）を差し替えれば、別の規則のソブリンロールアップになります。読む部分は `src/symbol.rs`、確定と先頭の 2 つの状態の作り方は `src/follow.rs` にあります。
