# Symbol を掲示板にして、ディーラーなしで鍵を作る（DKG）

FROST（Ed25519）のしきい値の鍵を、**誰も鍵の全体を一度も知らないまま**、参加者で分けて作る例です。参加者のやりとりは、全部 Symbol のメッセージに載せます。Symbol のハードフォークは要りません。

作った鍵で、預かり口座も回します。

- 預かり口座の鍵（①）と、委員会の鍵（②）を DKG で作る
- 預かり口座を、②だけを連署者にした 1-of-1 のマルチシグにする。①の鍵は、もう何にも使えない
- 委員会が入れ替わるときは、新しい委員会の鍵（③）を DKG で作り、連署者を②から③に差し替える。トランザクション 1 つで済み、預かった XYM は動かさない

使う暗号は、Symbol の署名と同じ Ed25519 の群と、分け前を暗号化する X25519 と ChaCha20-Poly1305 だけです。DKG の計算は Zcash Foundation の [frost-core](https://crates.io/crates/frost-core) の `keys::dkg` に任せ、この例で書いたのは、掲示板に載せる形と、苦情と明かしの手順です。

試作です。参加者はみなこのプロセスの中にいて、分け前はメモリにしかありません。本物の資産を預けるものではありません。

## 動かす

要るもの：

- Symbol のノードの REST。heika のノードなら、設定に検索表 `storage.search: [Transactions]` を入れておきます（掲示板を検索で読むため）
- 手数料を払う中継役の鍵。XYM を持っているもの

```sh
cargo build --release
./target/release/dkg run peer.yaml [1 段階のブロック数] < 中継役の秘密鍵
```

- `peer.yaml` は `heika experimental peer start` と同じ設定です。ここからネットワークと REST（最初の `rest` の口）を決めます
- 1 段階のブロック数の既定は 20 です。**ファイナライズの遅れより長くしてください**。参加者はファイナライズされたものを見てから動くので、短いと締め切りに間に合わず、正直な参加者が外されます
- 全員が載せた段階は、締め切りを待たずに閉じます。締め切りまで待つのは、載せない人がいるときだけです

`run` は、DKG を 3 回して、預かり口座の連署者を入れ替えるところまでやります。参加者は各 5 人で、署名に要るのは 3 人です。わざと不正をする参加者を 1 人ずつ入れてあります。

- ①：1 人が壊れた分け前を配り、苦情を受けて正しいものを明かす。誰も外れない
- ②：1 人が壊れた分け前を配り、苦情を受けても明かさない。外れて、残った 4 人でやり直す
- ③：1 人がずっと黙っている。外れて、残った 4 人でやり直す

```
[① 預かり口座] セッション … を始めます（参加者 5 人、署名に要るのは 3 人、1 段階は 20 ブロック）
[② 委員会] セッション … を始めます（参加者 5 人、署名に要るのは 3 人、1 段階は 20 ブロック）
[① 預かり口座] 高さ 21403 で始まりました
[② 委員会] 高さ 21403 で始まりました
[① 預かり口座] 試み 0: 参加者 2 が、参加者 4 からの分け前に苦情を言いました
[② 委員会] 試み 0: 参加者 1 が、参加者 2 からの分け前に苦情を言いました
[① 預かり口座] 試み 0: 参加者 4 が、参加者 2 宛ての分け前を明かしました（コミットメントと合っています）
[① 預かり口座] 高さ 21448 で鍵ができました: T…
[② 委員会] 試み 0: 参加者 2 を外します（苦情を受けて、正しい分け前を明かしませんでした）
[② 委員会] 高さ 21459 の次から、残った人でやり直します（試み 1）
[② 委員会] 高さ 21492 で鍵ができました: T…
高さ 21502 で、預かり口座 T… を、②だけを連署者にしたマルチシグにしました（2.000000 XYM を入れました）
①の鍵で預かり口座から送ろうとすると、弾かれました: Failure_Heika_Rejected_When_Harvesting
[③ 新しい委員会] セッション … を始めます（参加者 5 人、署名に要るのは 3 人、1 段階は 20 ブロック）
[③ 新しい委員会] 高さ 21504 で始まりました
[③ 新しい委員会] 試み 0: 参加者 5 を外します（締め切りまでに約束しませんでした）
[③ 新しい委員会] 高さ 21524 の次から、残った人でやり直します（試み 1）
[③ 新しい委員会] 高さ 21564 で鍵ができました: T…
高さ 21575 で、預かり口座の連署者を②から③に差し替えました（預かった XYM は動かしていません）
②で預かり口座から送ろうとすると、弾かれました: Failure_Heika_Rejected_When_Harvesting

```

`Failure_Heika_Rejected_When_Harvesting` は、heika のノードが、ブロックを作るときの検証で弾いたトランザクションに付ける共通の理由です。catapult のノードなら、①のほうは `Failure_Multisig_Operation_Prohibited_By_Account` になるはずです。

### 掲示板を外から読む

参加者でなくても、セッションの ID さえ知っていれば、掲示板からグループ鍵まで計算できます。

```sh
./target/release/dkg observe peer.yaml <セッションの ID>
```

## しくみ

### 掲示板があれば、同期型の DKG でいい

DKG がむずかしいのは、ふつう、「どの参加者の配布を採用するか」を全員で一致させるところです。ネットワークが届く順番を保証しないと、人によって見えているものが違うからです。非同期の DKG は、そのために合意の仕組みを抱えています。

Symbol は「後から間に差し込めない掲示板」です。ファイナライズされたブロックを読めば、全員が同じものを同じ順番で見ます。なので、教科書の「全員に同じものを届けるチャネル（ブロードキャストチャネル）がある前提の DKG」がそのまま使えます。

- 締め切りはブロックの高さで決める。「締め切りまでに載ったもの」は、誰が読んでも同じ
- 同じ人が同じ段階に何度載せても、最初の正しいものだけを使う
- 何を採用するかは、掲示板だけで決まる（[`src/board.rs`](src/board.rs)）。参加者の手元の状態には頼らない

### 段階

1 回の試みは 4 つの段階に分かれます。段階は、その試みの参加者が全員載せたブロックで閉じ、次の段階が始まります。載せない人がいれば、段階が始まってから決めたブロック数のところ（締め切り）で閉じます。全員が正直なら、1 段階はファイナライズの遅れと 1〜2 ブロックで済みます。

1. **約束する**：Feldman のコミットメント（多項式の係数を点にしたもの）と、定数項の知識の証明と、自分宛ての分け前を暗号化してもらう X25519 の公開鍵を載せる。締め切りまでに約束しなかった人は外す
2. **配る**：ほかの参加者それぞれに、暗号化した分け前を載せる。締め切りまでに配らなかった人は外す
3. **苦情を言う**：届いた分け前がコミットメントと合わなかったら、その配り手に苦情を言う。合っていたら「苦情なし」を載せる。苦情がなければ、ここで鍵ができる
   - 「苦情がない」ことは、何も載せないと掲示板から読めない。苦情なしを載せてもらうのは、全員そろったら早く閉じるため。載せなかった人は、締め切りで苦情なしとみなす
   - 署名に要る人数（しきい値）以上の人から苦情を受けた配り手は、明かさせずに外す
4. **明かす**：苦情を受けた配り手は、その人宛ての分け前を平文で明かす。明かした分け前がコミットメントと合えば、苦情を言った人はそれを使う。明かさなかった配り手は外す

誰かを外したら、残った人で最初からやり直します。正直な参加者は外されないので、やり直すのは不正をした人の数までです。残りがしきい値より少なくなったら失敗します。

鍵ができたら、グループ鍵は全員のコミットメントの定数項を足したものです。掲示板に載っているので、誰でも計算できます。

### 苦情と明かし

分け前は暗号化して載せるので、正しいかどうかは受け取った本人にしかわかりません。そこで、苦情を受けた配り手に、その分け前を平文で明かしてもらいます（Gennaro たちの DKG と同じやり方です）。

- 明かした分け前は、誰でもコミットメントと照らし合わせられる。合わなければ、配り手が悪い
- 合っていれば、配り手は外さない。苦情を言った人は、明かされた分け前を使う
- 暗号文が壊れていたのか、苦情が嘘なのかは区別しない。どちらでも、明かされた分け前で先に進める

しきい値以上の人から苦情を受けた配り手は、明かさせずに外します。苦情を言った人の中に必ず正直な人がいるので、配り手が悪いことがはっきりしています。それに、しきい値の数だけ分け前を明かすと、その配り手の秘密が公開されてしまいます。

これなら、暗号文が正しく作られたことの証明（検証可能な暗号化）は要りません。分け前が 1 つ明かされても、その人の鍵の分け前は全員からの分け前の和なので、ほかの配り手の分が秘密なら漏れません。嘘の苦情で明かさせられるのは、苦情を言った本人宛ての分け前だけです。

### 分け前の暗号化

- 参加者は、試みごとに X25519 の鍵を作り直し、約束に公開鍵を載せる
- 配り手と宛先の組ごとに、X25519 で共有した秘密と、セッションの ID、試みの番号、組の番号、両方の公開鍵から、ChaCha20-Poly1305 の鍵を作る。鍵は 1 回しか使わないので、ノンスは 0 のまま
- 相手の公開鍵が小さい位数の点で、共有した秘密が 0 になるときは使わない

### 点は素数位数の部分群のものだけ

Ed25519 の曲線の点には、位数 8 までの小さい成分（ねじれ）が混ざりえます。コミットメントにねじれが混ざると、そのままグループ鍵に残ります。

- catapult の署名の検証は、余因子をかけない式（[s]B = R + [h]A）です。グループ鍵にねじれ T が混ざっていると、[h]T が消えるとき（h が T の位数の倍数のとき）しか署名が通らない
- 署名し直せば h が変わるので、たまには通る。でも、ずっとたまにしか通らない委員会になる
- 直すには、DKG をやり直して連署者を差し替えるしかない

なので、掲示板から読む点は、frost-ed25519 の読み方で、単位元でなく、素数位数の部分群に入っているものだけを受け付けます。署名のときの R にねじれが混ざっても、その回の署名が弾かれるだけで、署名し直せば済みます。

### 預かり口座

1. **マルチシグにする**：預かり口座（①の鍵）を、②だけを連署者にした 1-of-1 のマルチシグにする。預かり口座の中のトランザクションなので①が連署し、連署者に加わる側の同意として②も連署する
2. **①の鍵は使えなくなる**：連署者のいるアカウントが自分で署名したトランザクションは、catapult の `MultisigPermittedOperationValidator` が弾きます（`Failure_Multisig_Operation_Prohibited_By_Account`）。①の分け前が漏れても、預かり口座は動かせない
3. **差し替える**：`MultisigAccountModification` 1 つで、③を足して②を外す
   - 足す人と外す人は、同じトランザクションの別のリストに書ける。止められるのは、外すのが 2 人以上のとき、足す人が重なるとき、同じ人を両方に書いたときだけ（`MultisigCosignatoriesValidator`）
   - 外すのを含むと、連署の数は承認の最小数の代わりに削除の最小数で数える（`MultisigAggregateSufficientCosignatoriesValidator`）。1-of-1 なら②の連署 1 つで足りて、外される側の同意は要らない
   - 足す③は、加わる側の同意として連署する

FROST の分け前を配り直す仕組み（resharing）でも、グループ鍵を変えずにメンバーを入れ替えられます。ただ、古いメンバーが古い分け前を捨てずに持っていると、しきい値の人数が集まれば署名できてしまいます。連署者の差し替えなら、古い委員会はチェーンのルールで締め出されます。代わりに、入れ替えのたびにトランザクションが 1 つ要り、入れ替えたことはチェーンから見えます。

手数料は、どれも中継役が、アグリゲートに署名して払います。預かり口座にもグループ鍵のアカウントにも、手数料のための XYM は要りません。

### どこまでが確立された手法か

- **そのまま**
  - DKG の計算（多項式、コミットメント、知識の証明、分け前の確かめ、鍵の合成）は、frost-core の `keys::dkg` の `part1`〜`part3` そのもの。FROST の論文と RFC 9591 が前提にしている、知識の証明付きの Pedersen の DKG
  - 苦情、明かし、しきい値以上の苦情で外す、という手順は、Joint-Feldman の DKG（Gennaro たちの論文で整理されたもの）と同じ
  - 分け前の暗号化は、X25519 と AEAD のふつうの組み立て
  - 連署者の差し替えは、暗号ではなく、Symbol のマルチシグの機能
- **変えたところ**（どれも、いつ・誰で計算するかの手順で、計算の中身には触っていない）
  - 誰かを外したら、外した人を除いて**最初からやり直す**。Gennaro たちの DKG は、外した人の分を除いて（QUAL）そのまま進む。やり直すほうが、frost-core の計算をそのまま使えて、手順が単純になる
  - 締め切りに加えて、**全員が載せたら段階を閉じる**。そのために、苦情がなくても「苦情なし」を載せる

## 信じているもの

- **参加者の多数が正直であること**。署名に要る人数（この例では 3 人）が組めば、何にでも署名できます。DKG の途中でも、その人数が組めば鍵を知れます
  - 自分の分け前を漏らした人も、不正をした人に数えます。漏れた値が誰の分け前かは、掲示板から計算できる参加者ごとの検証用の公開鍵と照らせば、誰でも確かめられます
  - 漏れたら、その人を抜いた委員会を DKG で作り、連署者を差し替えます。古い委員会の分け前は、どれだけ集めても使えなくなります。漏れがしきい値の人数に届く前に差し替えないと、先に差し替えられてしまいます
  - 今の委員会がどれかは、預かり口座の今の連署者で決まります。差し替えが 2 つ出ても、先に承認されたほうだけが通ります
- **Symbol が掲示板として働くこと**。ファイナライズされたブロックは巻き戻らず、誰が読んでも同じ、という前提です。中継役が載せるのを拒んでも、参加者は自分で手数料を払って載せられます
- **締め切りに間に合うこと**。チェーンが混んで、正直な参加者の載せたものが締め切りに入らないと、その人は外されます。1 段階のブロック数は、ファイナライズの遅れと混み具合を見込んで決めます

Pedersen の DKG（この形の DKG）では、不正をする参加者が、グループ鍵の分布を少しだけ偏らせられることが知られています。Schnorr の署名（FROST も Ed25519 も）に使うぶんには、安全性が保たれることが示されていて、FROST の論文もこの DKG を前提にしています。

## やっていないこと

- **本物の、別々の参加者**。参加者はみなこのプロセスの中にいます。分け前もメモリにしかなく、止めたら作り直しです
- **黙る人がいても署名を続けること**。署名する人は全員が応じるものとしています。黙る人がいても続けるには、ROAST（[examples/roast](../roast)）を使います
- **誰を参加者にするか**。参加者は、始めるもの（セッション）を載せた人が決めます。勝手に入ってくる人を防ぐ仕組み（Sybil 対策）はありません
- **耐量子**。できる鍵が Ed25519なので、量子計算機があれば、公開されているグループ鍵から秘密鍵を計算できます。分け前の暗号化だけを耐量子にしても意味がないので、していません
- **catapult での確かめ**。プライベートネットは heika だけです。catapult が同じトランザクションを受け付けるかは、まだ確かめていません

## プライベートネットで確かめたこと

2026-10-30 に、heika 4 台（ハーベストと投票をする 3 台と、見るだけの 1 台）のプライベートネットで動かしました。ブロックはおよそ 7 秒ごと、ファイナライズは先端から 10 ブロックほど遅れます。1 段階は 20 ブロックです。

- ①：苦情を受けた配り手が正しい分け前を明かし、誰も外れずに、始めてから 45 ブロックで鍵ができた
- ②：分け前を明かさなかった配り手を外して、残った 4 人でやり直し、始めてから 89 ブロックで鍵ができた。やり直したあとの試み（全員正直）は、3 段階で 33 ブロックだった。1 段階は、ほぼファイナライズの遅れの分だけ
- ③：約束しなかった人を外して、残った 4 人でやり直した
- 預かり口座を、②だけを連署者にした 1-of-1 のマルチシグにできた。①の鍵で預かり口座から直接送ると弾かれた
- 連署者を②から③に、トランザクション 1 つで差し替えられた。そのあと、②で預かり口座から送ると弾かれ、③で送ると通った。預かり口座は、連署者 1 人、承認と削除の最小数が 1 のまま
- `observe` で②の掲示板を外から読むと、参加者と同じ経過をたどって、同じグループ鍵になった

ブロックを作ったのも、トランザクションを確かめたのも heika です。catapult が同じものを受け付けるかは、まだ確かめていません。

最初に動かしたときは、連署者の差し替えが弾かれました。差し替えのアグリゲートで、手数料を払う中継役が、中のトランザクションに何も署名していなかったからです。catapult は、アグリゲートの署名者も連署者の 1 人に数え、どれかの中のトランザクションに要る署名者であることを求めます（`MultisigAggregateEligibleCosignatoriesValidator`）。今は、中継役が中で何もしないときは、中継役から中継役への、中身のない転送を入れています。

その最初の実行は、段階を締め切りまで待つ版でした。①は 80 ブロック、②は 140 ブロックかかりました。全員が載せたら段階を閉じるようにしたのは、そのあとです。

## heika の使い方

- 掲示板は、受け箱に宛てた転送のメッセージです
  - 受け箱は、セッションの ID のハッシュを公開鍵の代わりにして作るアドレスです（`Address::from_public_key`）。誰も秘密鍵を持っていません
  - 載せるときは、`Transfer::new(宛先, モザイクなし, メッセージ)` を中継役が署名して出します。1 KiB に収まらなければ、`Aggregate` の中の転送に分けます。アグリゲートは全部入るか全部入らないかなので、途中の欠片だけが載ることはありません
  - 読むときは `GET /transactions/confirmed?recipientAddress=<受け箱>&type=16724&embedded=true&fromHeight=…&toHeight=…` で、`toHeight` に `/chain/info` の `latestFinalizedBlock.height` を入れます。アグリゲートの中の転送は `meta.aggregateHash` でまとめて、順につなげます
- 参加者の署名は、Symbol の鍵と同じ `PrivateKey::sign` と `PublicKey::verify` です。どちらも、catapult と同じく、メッセージをいくつかに分けたまま渡せます
- 預かり口座のトランザクションは、[`src/symbol.rs`](src/symbol.rs) の `setup`、`rotate`、`spend` で作ります。どれも中継役が署名する `AggregateComplete` です
  - 中のトランザクションは `EmbeddedTransaction::new(署名者, ネットワーク, 本体)` で作ります。預かり口座のマルチシグの変更や送金は、署名者を預かり口座にします
  - 手数料は `Transaction::fee_for(倍率, 連署の数)` で、あとから足す連署の分まで見込みます
  - アグリゲートの署名者（ここでは中継役）も、中のどれかのトランザクションに署名していないといけません。何もしないなら、自分宛ての中身のない転送 `Transfer::new(自分のアドレス, モザイクなし, メッセージなし)` を入れます
  - FROST の署名は、ふつうの Ed25519 の署名です。連署は `Transaction::hash` に署名して、`Aggregate::add_cosignature` で足します。連署を足してもハッシュは変わりません
  - `Transaction::verify_cosignatures` で、出す前に確かめられます
